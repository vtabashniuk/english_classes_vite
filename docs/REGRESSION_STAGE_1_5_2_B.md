# CRM — 1.5.2b: інтеграційний контроль RLS/RPC (перша серія)

## Призначення

Перша серія `pgTAP` перевіряє **фактичні** PostgreSQL-права доступу, RLS і кілька критичних RPC, а не лише React-утиліти. **Жодних змін у бізнес-коді або SQL-міграціях немає.**

- `01_rls_rpc_isolation.sql` — 23 перевірки ізоляції двох викладачів і двох учнів: профілі, зв’язки, матеріали, платежі; заборона створення уроку для чужого учня; заборона відкликання матеріалу чужим викладачем або учнем; успішне відкликання та відновлення власним викладачем.
- `02_security_contracts.sql` — 17 перевірок увімкненого RLS, табличних привілеїв, заборони виклику планувальника та наявності тригера незмінності фінансового журналу.

Всього: **40 SQL-assertions**, додатково до 81 швидкого JS-тесту. Перевірка фактичної фінансової бухгалтерії (транзакційні RPC, податкові розрахунки) і календарних операцій для дозволеного учня **ще не входить** до цієї серії.

## Безпечний порядок запуску (PowerShell)

1. Переконайтеся, що знаходитеся в гілці `feature/regression-stage-1-5-2`, що зміни 1.5.2a вже закомічені. Розпакуйте цей ZIP поверх кореня CRM.
2. Переконайтеся, що Docker Desktop запущено. У корені CRM виконайте:

```powershell
npx supabase status
```

Якщо **локальний** Supabase не запущено, допустимо виконати `npx supabase start`. **Не виконуйте** `supabase db reset`, `supabase db push` та жодних команд із `--linked`.

3. Запустіть тести тільки таким чином:

```powershell
npx supabase test db --local
```

**УВАГА:** не запускати `npx supabase test db --linked` та не передавати `--db-url`, URL чи ключі Production. SQL-перевірки працюють з `auth.users`, `teacher_students`, `materials` та `payments`; їх запускати можна **виключно в локальній БД**. Перевірка імені бази в SQL — тільки додаткова діагностика, вона не відрізняє хмарний Postgres від локального.

4. Надішліть консольний вивід команди. Очікування: два файли з позначкою `ok`, `Tests=40`, `Result: PASS`. Навіть якщо тести пройшли, це **не свідчить про виконання всіх бізнес-сценаріїв**: це лише перший інтеграційний набір.

## Ізоляція тестових даних

- Вставляються лише синтетичні локальні користувачі з доменом `.invalid` та фіктивними паролями, без надсилання листів.
- Обидва SQL-файли використовують транзакцію `BEGIN … ROLLBACK`; pgTAP runner також ізолює кожен файл власною транзакцією. Не повинно залишитися тестових користувачів, матеріалів чи платежів.
- Запит не виконує Production API-запитів, не записує файли до Storage й не змінює міграції.
- У поточний GitHub Actions `Quality checks` ці тести **навмисно не включені**: CI не має локального PostgreSQL і не повинен отримувати Production-ключів.

## Якщо тест упав

Не виправляйте автоматично перевірену бізнес-логіку. Збережіть перше повідомлення `not ok` та SQL-помилку, перевірте стан локальних міграцій і передайте результат для аналізу. У разі збою спочатку виправляємо тест/фікстуру або уточнюємо очікування; SQL-міграції — лише після встановлення реальної проблеми.

## Статус

Набір перевірено статично (кількість assertions, транзакційні межі, підписи RPC та назви таблиць звірені зі станом 1.5.1). У середовищі підготовки немає запущеного PostgreSQL/Docker, тому **фактичний тестовий запуск на локальному Supabase ще не підтверджено**.
